# Human Use 首版方案

冻结日期：2026-10-15。状态：v1 开发基线。

## 目标与边界

AI 通过本机 HTTP API 发起需要人完成的请求，人通过浏览器填写和提交，AI 读取证据并验收，验收通过后形成可按 SHA-256 检索的工单包。首版只供运行软件的电脑使用。应用数据、附件、归档和前端资源保存在本机，不使用云存储、遥测或外部 CDN。接入的 AI 客户端是否向云模型发送读取内容，由该客户端和使用者控制。

采用 Node.js 24、内置 HTTP 服务、内置 SQLite、原生 HTML/CSS/JavaScript，无第三方运行时依赖。相较讨论中的 Python 建议，选择本机已可用的 Node.js，以减少安装和交付成本。运行地址默认 http://127.0.0.1:4317。

## 交互与状态

工单包含标题、目的说明、来源项目、验收标准和有固定 ID 的任务单元。支持 checklist、文本、数值（含单位）、单选或多选、图片及文件附件。文本可使用操作系统语音输入，不实现录音转写。

状态为 pending（待处理）、submitted（待验收）、returned（需补充）、blocked（无法完成）、archived（已归档）、cancelled（已取消）。人可保存草稿、报告阻塞、恢复处理、提交；AI 可通过或退回最新提交，也可取消未归档工单。首版没有用户体系，页面代表本机操作者，API 代表接入的代理；不提供身份认证或签名证明。

提交要求必填项满足完成条件，生成不可覆盖的版本快照和提交哈希。提交后不允许改写该快照；退回保留快照、理由和事件，补交生成新版本。AI 验收显式绑定提交版本及哈希。归档后禁止修改；继续工作需另建关联工单。

## 数据与归档

默认数据目录为项目内 data，可用 WORKORDER_DATA_DIR 指定独立目录。SQLite 保存请求、草稿、提交、验收和事件。附件使用服务生成的 ID 命名，保留原文件名作为元数据，单文件上限 20 MiB。

归档包含 ticket.json、submissions/、attachments/、reviews.json、events.json 和 manifest.json。清单记录所有业务文件的路径、字节数和 SHA-256，按路径排序，以固定 JSON 序列化输出。manifest 不列自身；其字节的 SHA-256 是包的完整内容标识。ZIP 只是导出载体，不作为内容哈希计算对象。

归档先完整写入临时目录，再重命名为完整哈希目录，最后提交数据库归档状态；失败不得留下已归档的数据库状态。完整性检查重新计算 manifest 哈希及所列文件哈希，并检查额外文件。哈希验证内容一致性，不证明物理动作真实发生或操作者身份。

## AI 集成

先交付 HTTP API Bridge 和命令行调用示例；MCP 封装后续复用相同业务接口，不在首版实现第二套协议。API 支持创建、按来源及状态查询、读取详情和附件、验收、取消、按哈希读取归档及校验、ZIP 导出。

来源 source 与 request_key 组合用于幂等创建；相同键和不同请求返回冲突。AI 建单即返回 ID 和本机网页链接，后续查询状态；不承诺自动唤醒 AI 会话。页面定时刷新列表和非编辑详情，不覆盖未保存内容。

## 访问边界

仅监听 127.0.0.1；检查 Host 和 Origin，不开放跨域访问。API Bridge 使用本地生成的 Bearer token；网页使用 HttpOnly、SameSite=Strict 会话 Cookie。上传类型和大小、任务数据契约、状态转换、附件归属、并发草稿版本在各自入口检查一次。附件路径不得由用户指定，非允许预览的图片以下载方式提供。工单内容按文本渲染，不执行 AI 提供的 HTML 或脚本。

## 页面与验收

页面包括工单列表与筛选、任务处理详情、历史提交与验收、归档查询及校验。提供显式创建示例工单的入口，不在首次启动时自动塞入演示数据。

验收案例：创建五类单元工单 → 保存草稿与上传图片 → 提交 → AI 退回 → 人补交 → AI 通过 → 按哈希检索并导出 ZIP → 重启后读取 → 篡改附件后校验失败。另覆盖必填项缺失、过期验收、草稿版本冲突和本机访问边界。使用 Node.js 内置测试器与浏览器实际交互检查，不引入测试框架。

不包含多人权限、云同步、手机访问、远程 MCP、通知推送、任意脚本执行、工作流设计器或模型内置调用。
